# PostgreSQL module consolidation: preparation and cutover

Status: the import and PostgreSQL module connection require an end-to-end rehearsal against a disposable PostgreSQL database before any VM cutover. The local automated suite skips its PostgreSQL integration test when `ITOM_TEST_POSTGRES_URL` is not set. Do not run the import against production until rehearsal and backup restoration have succeeded.

The application retains separate primary and module migration histories. Primary revisions 0011–0013 already create the same five module tables as module revision 0001. On a single database, **do not run both migration upgrades blindly**: that attempts to create the same tables twice. Inspect the actual VM database revision, existing tables, schema definitions and row counts before deciding the migration path. Never stamp a migration merely to bypass an error.

## Rehearsal and VM inventory

1. Identify the running service, PostgreSQL host/database/version and the actual SQLite `DATABASE_URL_2` file without exposing credentials. Confirm where attachment bytes and source workbooks reside. The documented server-wide file is `C:\ProgramData\ITOM\data\modules.db`, but the active configuration is authoritative.
2. Establish a maintenance window and stop writes, including the portal's module writes and telemetry scheduler. Use SQLite's online backup API for a consistent module snapshot, and PostgreSQL `pg_dump` for the primary database. Preserve runtime configuration and required workbooks securely. Keep copies outside the VM and verify restores into isolated test systems. A file copy of a live SQLite database without its WAL is not a valid backup procedure.
3. Restore the PostgreSQL backup into a disposable staging database. Inspect primary and module Alembic revisions and all module tables. If the primary migration has created the five module tables, compare their definitions with the current migration and check every table is empty. If tables already contain records, stop: determine their ownership and reconcile explicitly. Do not overwrite them.
4. On staging, apply the reviewed primary migrations. If their 0011–0013 revisions have created exactly the expected module schema, and the module version table is absent, after validating schema equivalence record module revision 0001 using `python -m alembic -c alembic-modules.ini stamp 0001_module_storage`. This is appropriate only for a verified equivalent schema. If the table structure, data, or migration history differs, design a specific reconciliation rather than stamping.
5. Configure `DATABASE_URL` and `DATABASE_URL_2` to the same staging PostgreSQL database using the protected runtime environment. Keep secrets out of command lines, logs and source control. Point `DATABASE_URL_2` to a PostgreSQL role permitted to read and write the module tables and sequence values. Keep source systems disabled during rehearsal.
6. Run `python scripts/import_module_data.py <path-to-frozen-sqlite-backup>`. It requires both migration revisions, refuses nonempty target tables, locks those tables, copies all rows including deleted records, JSON, reviews and file bytes, compares imported values inside the transaction, and advances integer ID sequences. Source datetimes without a timezone are interpreted as UTC; validate this assumption against the VM data before import. It does not merge datasets. Do not rerun against populated tables.
7. Run `ITOM_TEST_POSTGRES_URL`-configured isolated PostgreSQL integration tests and the module API/browser tests against staging. Verify counts and attachments against the snapshot, create/edit/review records, restart the application and confirm they remain visible, test telemetry reads and both readiness endpoints. Do not seed or test against production data.
8. After successful rehearsal and an agreed window, repeat the controlled snapshot, migration and validation on the VM. Restore writes only after verifying the application and monitoring. Retain the old SQLite snapshot and pre-cutover PostgreSQL backup. Once new PostgreSQL writes occur, rollback requires reconciling those writes; do not silently switch back to SQLite.

The import is not a replacement for ongoing backups. Configure scheduled, encrypted and access-controlled PostgreSQL backups, off-VM retention, periodic restore tests and, where required, point-in-time recovery. Back up external workbooks and any separately stored attachments as well.
