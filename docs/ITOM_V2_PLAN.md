# ITOM V2 audit and delivery plan

Audit date: 2026-10-27  
Baseline: `80783d757750edff301ff345c4319cc10bdf1f0f`, branch `feat/itom-v2-tailwind`  
Scope: current React/TypeScript portal in `frontend-revamp/`, served assets in `frontend/`, FastAPI, repositories, data models, source adapters and tests. This is a static and isolated-test audit; no live sync, live database access, schema changes, deployment, or application code changes were performed. Findings about runtime scale require confirmation against representative, sanitized data.

## Executive assessment

The application already has useful foundations: source-key uniqueness and active-record scoping, bounded core inventory pages, source freshness metadata, read-only SWIS guards, snapshot reconciliation and substantial isolated tests. V2 should first close correctness and product-boundary gaps, then reduce repeated work on the paths actually measured. Avoid redesigning ingestion or merging source identities simply to improve dashboard appearance.

## SQL and database evidence

Current ORM metadata (`app/models/ci.py`) defines `(source_system, is_active)`, unique `(source_system, source_id)`, `(source_system, ci_type, status)`, and individual name, location, location ID, status, vendor and other indexes. The unique key supports the per-record sync lookup, but does not eliminate N+1 round trips. Actual deployed indexes and statistics have not been inspected; migration `0004_sqlite_query_indexes.py` is a marker with a no-op upgrade, so verify deployed schema explicitly before proposing migrations. SQLite applies an active-row loader criterion on ORM selects (`app/core/database.py`); preserve this behavior when rewriting SQL. PostgreSQL is also supported and needs its own plans and tests.

Controlled local benchmark: Python `sqlite3`, in-memory synthetic table with 50,000 rows, 95% active, 75% Intune, 100 location IDs, relevant modeled indexes, one warm-up and 20 timed executions; median and 19th sorted sample as approximate p95. Representative SQL shapes, not exact SQLAlchemy-generated statements or production schema/data; no network, ORM serialization, concurrency, live data or cold-cache cost. SQLite optimizer choices and results will vary. Times are not an SLA.

| Query shape | Median / p95 ms | `EXPLAIN QUERY PLAN` evidence |
|---|---:|---|
| Active Intune page, order name, limit 25 | 8.379 / 9.721 | Search `ix_ci_source_active`; temporary B-tree for order |
| Active Intune count | 1.414 / 1.747 | Covering `ix_ci_source_active` search |
| Active Intune six-field case-folded substring search and page | 52.987 / 57.508 | Source index search plus temporary B-tree; leading wildcards still scan candidate values |
| Active normalized `lower(trim(location))` count | 13.359 / 20.864 | Full table scan; ordinary location index cannot serve that expression |
| Active SolarWinds JSON category count | 5.297 / 6.251 | Source index search; category expression evaluated on candidate rows |
| Active location-ID page ordered by name and ID | 0.266 / 0.307 | Location-ID index search; temporary B-tree for order |

Candidate experiments, not approved schema changes: compare `(source_system, is_active, name, id)` for the common source page and `(location_id, is_active, name, id)` for location pages against actual plans, write amplification and data distributions. Test expression/generated-column or normalized-field indexes only where actual query expressions and SQLite/PostgreSQL support match; existing simple indexes do not generally accelerate `lower(trim(...))`, JSON extraction or leading-wildcard search. Evaluate FTS or a deliberately limited search contract for multi-field substring search, with correctness and privacy review. Indexes must be migration-managed, reversible and benchmarked against ingestion overhead; do not add all candidates speculatively.

Other expensive paths to instrument: resource-pressure filter reads every active SolarWinds attributes object then constructs an ID list before count/page (`ci_repository.py`); large ID lists may hit dialect parameter limits. `_storage_metrics` and decision summaries separately load JSON attributes; group assessments load group, membership, node and location data and may retry observation-token checks up to three times. `observation_token` itself scans/aggregates inventory and reads rules/locations twice per attempt. Location catalogue computes multiple issue counts across groups. Capture query counts, bytes and p50/p95 endpoint times at 10k/50k/representative fleet sizes, with cold/warm cache and concurrent sync, using sanitized copies and matching baseline hardware. Record exact SQL and EXPLAIN, indexes, SQLite version and statistics; do not run write-generating app startup or sync against a live DB.

Core CMDB, Intune and SolarWinds inventory endpoints accept filters, allowed page sizes and sort parameters (`app/api/v1/endpoints/{cmdb,intune,solarwinds}.py`); filtering/count/offset are generally server-side. Location devices are an exception as noted above. Offset cost grows for deep pages. Source/category JSON and case-folded fields deserve plan verification. Group devices have their own recursive group traversal, filters and ordering (`solarwinds_group_repository.py:133-168`); compare requested UI filters with endpoint support before claiming parity. Count and page are separate reads and are not a cross-request immutable snapshot.

## Metric and evidence contract

For each KPI, define a stable metric ID, source and population, numerator/denominator or count, exclusions, calculation and units, observed-at and last successful ingestion, freshness/coverage, unknown/empty behavior, threshold and policy version, and exact drill-down filter. Definitions must appear beside or one action away from the metric; a disabled action needs a reason. CSV exports must preserve the same filters and formula neutralization.

| Current metric family | Existing semantics to retain or clarify | Required drill-down / verification |
|---|---|---|
| Managed endpoints, Intune compliance and noncompliant | Active Intune source records; confirmed compliant divided by all active endpoints including unknown states. Noncompliant is confirmed state, not all unknown/error. | All endpoints or exact matching status; compare counts, unknown and zero denominators. |
| SolarWinds nodes, Up ratio, low-health and resource pressure | Active node records; Up ratio excludes explicit unmanaged and includes unknown in eligible population. Pressure is observed CPU >=75% or memory >=80%, not sustained utilization; show reading coverage. Low tier is a persisted classification, not measured resource health. | Matching nodes and threshold evidence; validate null, invalid and one-sided readings, source status and freshness. |
| CMDB source records and source-system count | Active source records, not necessarily distinct physical assets; source systems are the distinct populated sources. | Source-filtered records and source distribution; reconcile each population and disclose cross-source duplication. |
| Regular groups / attention / location health | Native regular SolarWinds groups at mixed levels; group membership can overlap. Attention is based on warning/critical/down native group status. Group score is a separately derived policy with documented eligibility. | Group selection and matching unique descendants; show mixed levels, overlap, status versus score and score inputs. |
| OS distribution, health/status/category charts, geographic matches | Counts partition reported values subject to unknown/unclassified handling; geographic match is approximate city/country/region evidence, not office identity or a combined score. | Click to matching inventory where supported; expose unassigned, conflicting and unavailable evidence, avoid summing overlapping geographic rows. |
| Location scores and forecasts | `docs/LOCATION_SCORECARDS.md` documents weighted policy, coverage and mapping constraints; `docs/DECISION_METRICS.md` distinguishes current observations from SLA. Forecast is model-derived, not future telemetry. | Show policy version, actual denominators, coverage and exclusions, source timestamps; history only from stored observations and explicit forecast assumptions. |

Inventory should expose source and per-record observation where relevant; aggregate cards need source-specific freshness, not merely a global status. Current code already has loading, retry and no-match states (`Inventory.tsx:361-378`), and uses unavailable placeholders in multiple places; preserve these strengths while testing the difference among no results, no successful snapshot, stale last success and failed latest attempt. Search, sort, filtering, pagination, export and drill-down must share a single population contract, with accessible focus restoration, keyboard operation and responsive layout.

## Source pipelines and data integrity

- Intune: Graph client follows `@odata.nextLink`, validates pagination URLs, refreshes a token once and uses timeouts (`src/sync/graph_client.py`). Preserve origin validation, partial-page failure behavior and source identity; measure page counts, throttling, missing fields and extracted/normalized/rejected/persisted counts without logging credentials or personal data.
- SolarWinds: `src/sync/solarwinds_client.py` enforces GET and validates read-only SWQL; preserve TLS verification, timeouts and request guards. Verify that V2 never sends writes to SolarWinds. Group and node inventories are separate evidence; missing or incomplete groups must not be conflated with zero nodes.
- `sync_service.py` uses a transaction-scoped PostgreSQL advisory lock, process-local SQLite lock, source-key fingerprinting and history on change. Only validated complete snapshots may retire absent records; failures/partial runs must not advance last-success freshness. Tests must cover interrupted pagination, duplicate IDs, malformed records, partial groups, unchanged records, atomic rollback, restart and two concurrent schedulers. Source freshness is ingestion recency, not device check-in recency or historical uptime.
- Location resolver and geographic dictionaries are explicit heuristics, not authoritative physical-location truth. Preserve raw labels, approvals and provenance; review ambiguous and conflicting cases without silently linking offices. Keep TechAdmin separate from ITOM.

## Delivery order and release gates

1. **P0 — trust and boundary:** remove TechAdmin from ITOM, implement per-panel asynchronous states and prove zero/unknown/failure semantics. Owner: product + frontend/backend. Gate: mocked partial failures, successful empty snapshots, retry and accessibility checks.
2. **P1 — metric and navigation contract:** inventory every KPI and chart against the table above, connect exact drill-downs and source timestamps; fix misleading search and unsupported filters. Gate: numerator/filter reconciliation tests, CSV parity, keyboard and narrow-screen browser journeys.
3. **P1 — database and ingestion scale:** capture production-like plans on an isolated sanitized snapshot; eliminate measured N+1 and unbounded reads, then test candidate indexes and migration plans for SQLite and PostgreSQL. Gate: before/after query count, warm/cold latency and memory with identical data; rollback and ingestion correctness tests. Agree measurable p95 targets with operators after baseline measurement.
4. **P2 — maintainability and progressive loading:** split large modules, normalize contracts compatibly, reduce unnecessary calls and profile UI payload/render. Gate: API compatibility, cache/freshness race tests, frontend data tests and browser journeys.

Existing useful checks: `npm --prefix frontend-revamp test`; `python -m pytest tests/browser/test_figma_revamp.py --run-browser -q`; focused `python -m pytest tests/test_canonical_locations.py -q`, plus source safety, reconciliation, cache, scheduler, API and migration suites on isolated databases. At this baseline the preceding preparation run passed 9 frontend tests, 42 location tests and 17 browser tests; these are not a fresh performance or production validation. Do not run live sync as a smoke test. Security and deployment changes need separate authorization and an operational rollout plan.

## Open decisions and residual risks

- Establish authoritative KPI owners, expected fleet sizes, endpoint SLOs, target browser/device profiles and retention requirements before setting budgets.
- Obtain an explicitly authorized sanitized representative database or a safe read-only measurement environment to confirm real query plans, deployed indexes and production latency. No production performance claim follows from the synthetic sample.
- Agree whether group status, score and geographic matches belong on the home screen and what approved navigation should replace the TechAdmin link.
- Confirm shared-access identity and authorization model, SQLite single-process scheduler policy, and PostgreSQL deployment requirements before implementation.
